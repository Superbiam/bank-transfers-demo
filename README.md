# Bank Transfers API

Тестовое задание на позицию Senior Backend-разработчика: сервис для работы с клиентами банка, их счетами и картами, включая переводы между счетами (в том числе в разных валютах).

Сразу о главном, чтобы не пришлось искать по тексту: **ядро системы готово и проверено на реальной PostgreSQL, а HTTP-слоя пока нет.** Переводы, идемпотентность, закрытие счёта, выпуск карт и защита номеров карт работают и покрыты 198 тестами, включая конкурентные. REST-контроллеров, JWT, клиентов с телефонами и выписки в этой версии нет. Сделать больше можно было, но я решил в моменте сделать упор именно на базу и domain сущность тестами, чтобы убедиться в том, что система работает минимально неправильно.

## Как запустить

Нужен Docker. JDK 21 нужен только для локального запуска тестов вне контейнера.

```bash
cp .env.example .env        # заполните значения, см. ниже
docker compose up --build   # PostgreSQL и приложение, миграции Flyway накатываются при старте
```

Приложение собирается в контейнере (двухстадийный `Dockerfile`, запуск от непривилегированного пользователя) и слушает порт 8080. Миграции и демо-данные накатывает само приложение при старте.

В `.env` задаются `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `PAN_ENCRYPTION_KEY` и `PAN_HMAC_KEY`; `JWT_SECRET` заведён заранее под будущую аутентификацию. Для шифрования номеров карт нужны два **разных** ключа по 32 байта в base64:

```bash
openssl rand -base64 32     # PAN_ENCRYPTION_KEY
openssl rand -base64 32     # PAN_HMAC_KEY
```

Без ключей приложение не стартует, и это сделано намеренно (проверено: если убрать ключ из `.env`, контейнер падает). В репозитории лежит только `.env.example` без значений. При запуске не через Compose (из IDE) файл `.env` не читается, переменные нужно задать в конфигурации запуска.

### Тесты

```bash
./mvnw test
```

Нужен запущенный Docker: интеграционные тесты поднимают PostgreSQL через Testcontainers. На момент написания проходят 198 тестов, ошибок нет. Ключи для тестов фиксированные и ненастоящие, они лежат в тестовой конфигурации.

## Стек

Java 21, Spring Boot 4.1.2, Maven, PostgreSQL, Flyway, Testcontainers.

Я выбрал Java и Spring Boot, потому что на них уверенно пишу промышленный код и потому что для этой задачи у стека есть всё нужное: зрелая модель транзакций, блокировки строк через JPA и SQL, Bean Validation и Spring Security для следующих шагов. `BigDecimal` из стандартной библиотеки даёт точную десятичную арифметику без внешних зависимостей, а Flyway даёт версионируемые миграции, которые ТЗ требует отдельно.

## Архитектура

Четыре слоя, зависимости направлены внутрь:

- **domain**: сущности и правила (деньги, счёт, карта, перевод). Ничего не знает про Spring, JPA и HTTP, поэтому правила проверяются обычными unit-тестами без контекста.
- **application**: сценарии (перевод, закрытие счёта, выпуск карты, смена статуса). Здесь границы транзакций, блокировки и идемпотентность. Порты (интерфейсы хранилища и поставщика курсов) лежат в `application.port`.
- **infrastructure**: JPA-сущности и адаптеры портов, шифрование номеров карт, заглушка курсов, фоновая очистка ключей идемпотентности.
- **api**: контроллеры, DTO, глобальный обработчик ошибок. **Этот слой ещё не написан.**

Пакеты разложены по смыслу, а не по технической роли: `application.transfer`, `application.card`, `domain.entity.account`, и так далее. Всё про один сценарий лежит рядом.

## Ключевые решения

У каждого решения: контекст, выбор и почему не другой вариант.

### Деньги: `BigDecimal` и scale валюты
Суммы должны содержать ровно столько знаков, сколько допускает валюта (USD 2, JPY 0, KWD 3). Я использую `setScale(..., UNNECESSARY)`: лишние знаки отклоняются ошибкой, а не обрезаются молча. В БД `NUMERIC(19,4)`. Не `double` из-за двоичной погрешности, не молчаливое округление ввода (клиент не узнает, что сумма изменилась) и не `long` в минорных единицах (неудобно с курсами и валютами разной точности).

### Строгий формат суммы
`new BigDecimal(String)` принимает экспоненту, а `setScale` на `1E999999999` пытается построить число с миллиардом нулей: это дешёвый способ положить сервис. Поэтому формат проверяется регулярным выражением до парсинга: до 18 цифр в целой части, до 4 в дробной, без экспоненты, знака `+`, запятой, `.5` и `5.`. Проверка живёт в домене, а не только в DTO: инвариант не должен зависеть от того, что контроллер ничего не забыл.

### Конвертация: `HALF_EVEN`, одно округление в конце
Курс умножается на сумму без потери точности, потом одно округление до знаков целевой валюты. Банковское округление не копит смещение вверх на больших объёмах, в отличие от `HALF_UP`. Промежуточных округлений нет: они накапливают ошибку. Курс хранится с 8 знаками (`NUMERIC(19,8)`), лишние знаки отклоняются, а scale нормализуется, чтобы `0.92` и `0.920` были равны по `equals`.

### Курсы: абстракция и заглушка
Переводы в разных валютах реализованы, а не отклоняются. За источник курсов отвечает интерфейс `RateProvider`, сейчас за ним стоит заглушка с фиксированными курсами для нескольких пар (USD, EUR, KGS, JPY, GBP). Неизвестная пара даёт ошибку `RATE_UNAVAILABLE`. В операции сохраняются обе суммы и курс, чтобы любую цифру можно было воспроизвести без пересчёта. Сам домен курсы не ищет: курс приходит параметром, а домен проверяет, что пара совпадает со счетами.

### Конкурентность: пессимистичная блокировка
Параллельные переводы с одного счёта не должны давать потерянное обновление и овердрафт. Я блокирую оба счёта одним запросом `SELECT ... FOR UPDATE ... ORDER BY id`: единый порядок захвата исключает взаимные блокировки. Сверху стоит `CHECK (balance >= 0)` как последний рубеж. Не оптимистичная версия с повтором: на горячем счёте конфликты частые, и повторы обходятся дороже ожидания блокировки.

Я проверял, что тесты действительно защищают это решение, а не просто проходят. Если брать счета по одному в порядке аргументов, тест встречных переводов (A→B и B→A) падал с дедлоком во всех пяти повторах. Без `@Lock(PESSIMISTIC_WRITE)` деньги спасает `@Version` (видны ошибки оптимистичной блокировки, но суммы не портятся). Явный `ORDER BY` я оставил, хотя без него дедлок не воспроизвёлся: PostgreSQL по первичному ключу отдаёт строки в порядке индекса. Но это свойство плана запроса, а не гарантия, и полагаться на него нельзя.

### Версия записи как вторая линия
Поле `version` увеличивает только слой хранения (`@Version`), домен его не трогает. Оно защищает изменения счёта, которые идут не через перевод, и ловит путь кода, который забыл взять блокировку.

### Идемпотентность переводов
Ключ генерирует клиент, поэтому уникальность задаётся парой `(user_id, key)`: глобальная уникальность позволила бы получить чужой результат, угадав ключ. Ключ регистрируется `INSERT ... ON CONFLICT` в той же транзакции, что и сам перевод. Если ключ просрочен, он перезаписывается. Вместе с ключом хранится хэш запроса (считается от нормализованных значений, поэтому `10` и `10.00` дают один хэш): тот же ключ с другим телом отклоняется ошибкой.

Состояния "в процессе" нет, и это упрощение сознательное: параллельный повтор ждёт на уникальном индексе, пока первая транзакция не завершится. Если первая откатилась, ключ освобождается и вторая выполняется заново. Если зафиксировалась, вторая отдаёт готовый результат. Из этого следует важное свойство: отказ по бизнес-правилу (например, недостаточно средств) ключ не "сжигает", потому что регистрация откатывается вместе с транзакцией. Это покрыто отдельным тестом. Срок жизни ключа ограничен, просроченные удаляет фоновая задача. Не кэш в памяти: он не переживает перезапуск и не работает с несколькими экземплярами.

### Домен на чистом Java, без JPA
Правила баланса, закрытия счёта и статусов карты живут в доменных классах, а маппинг на таблицы делает отдельный слой. Не аннотации прямо на доменных сущностях: так меньше кода, но правила привязываются к ORM, а тесты тянут за собой контекст Spring.

### Слой хранения: связи по UUID, порты там, где есть домен
В JPA-сущностях нет `@ManyToOne` и `@OneToMany`, только идентификаторы: связанные данные нельзя загрузить случайно (N+1). Порты лежат в `application.port`, потому что интерфейс принадлежит тому, кто им пользуется, а домен про хранилище не знает; адаптеры живут в `infrastructure.persistence`. Для клиентов и телефонов, где доменной логики нет, я не планировал порты: это был бы порт ради порта.

### Вставки и изменения в JPA
Вставка с заданным приложением `id` идёт через `EntityManager.persist` или нативный SQL, а не через `save`: для сущности с известным `id` `save` вызывает `merge` и делает лишний `SELECT`. Изменение идёт через управляемую сущность, загруженную под блокировкой. Версию из домена в сущность не копируют: ею владеет только слой хранения. После вставки операции стоит явный `flush`, потому что ключ идемпотентности ссылается на неё внешним ключом, а запись ключа идёт через JDBC и выполняется сразу.

### Ошибки доменного слоя несут код, а не HTTP-статус
`DomainException` содержит машинно-читаемый код, а соответствие кода и HTTP-статуса задаётся в одном месте (глобальный обработчик, он ещё не написан). Не `@ResponseStatus` на исключениях: домен не должен знать про HTTP.

### `null`: NPE или доменное исключение
Если значение формируется внутри системы (актор из JWT, целевой статус из DTO), `null` означает баг, и громкий `NullPointerException` честнее аккуратной бизнес-ошибки. Если значение может прийти от клиента (суммы, причина смены статуса), инвариант защищается доменным исключением. `compareTo(null)` бросает NPE по контракту `Comparable`.

### Закрытие счёта и карты
`Account.close(hasActiveCards)` получает флаг от сервиса, который считает его запросом `EXISTS` под блокировкой счёта. Не коллекция карт внутри `Account`: загрузка ради одной проверки это N+1. Активной считается карта со статусом `ACTIVE` и не вышедшим сроком: просроченная по дате карта закрытие не блокирует, иначе счёт нельзя было бы закрыть до запуска фонового джоба. Порядок блокировок везде один: сначала счёт, потом карта. Выпуск карты и закрытие счёта берут блокировку счёта, поэтому не могут разойтись.

### Номер карты не хранится открыто
Полный номер не попадает в логи и ответы API. Класс `CardNumber` проверяет формат и контрольную сумму (алгоритм Луна), а в `toString()` отдаёт маску, чтобы номер нельзя было залогировать случайно. Агрегат карты хранит только маску. Для сборки маски из БД без расшифровки хранятся первые шесть цифр, последние четыре и длина номера.

Сам номер шифруется AES-256-GCM со случайным nonce на каждую запись. В AAD идёт `id` карты, поэтому шифртекст нельзя перенести в строку другой карты. Формат колонки: байт версии ключа, nonce, шифртекст с тегом (версия нужна для будущей ротации ключа). Для проверки уникальности хранится HMAC-SHA256 под отдельным ключом: шифрование недетерминированное и по нему искать нельзя, а один ключ на две задачи ослабляет обе. Метода расшифровки в коде нет намеренно: ни один сценарий не отдаёт номер целиком, а лишний код это лишняя поверхность атаки. CVV не хранится.

Не только маскирование: оно необратимо и не позволяет проверить уникальность. Для реальной системы вместо этого нужна токенизация или HSM, ключи из переменных окружения подходят только для демонстрации.

### Срок карты и статусы
Срок хранится как последний день месяца (`10/33` значит `2033-10-31`). Карта просрочена, если сегодня (UTC) позже этой даты или в БД уже стоит `EXPIRED`. Время приходит параметром, поэтому тесты используют фиксированное. Не только фоновый джоб: до его запуска просроченная карта оставалась бы рабочей. Допустимые переходы заданы таблицей: `ACTIVE ⇄ BLOCKED`, `EXPIRED` конечное. Срок проверяется раньше таблицы переходов, поэтому разблокировка просроченной карты возвращает точный код `CARD_EXPIRED`, а не общий "переход недопустим". Порядок защищён тестами для обеих причин просрочки.

### История статусов карты
Смена статуса возвращает запись (кто, когда, почему, откуда, куда), сервис вставляет её в журнал в той же транзакции. Не коллекция внутри карты: её не нужно грузить ради смены статуса. Триггеры БД запрещают `UPDATE` и `DELETE` в этой таблице и в журнале операций.

### Удаление и схема
Клиенты удаляются мягко: на них ссылаются счета и журнал, который хранится вечно. Счета не удаляются, а закрываются, внешние ключи без `CASCADE`. Время закрытия счёта не хранится: по ТЗ оно не нужно, а аудит закрытия вынесен в "что доделал бы". Миграции после публикации не правятся, исправления идут новыми: `V3` исправила опечатку в статусе карты, выровняла ограничение телефона с валидацией, добавила `CHECK` статуса операции и связи курса с валютами и колонку длины номера.

### Тесты на реальной БД
Интеграционные и конкурентные тесты делят один контейнер PostgreSQL и один контекст приложения (общий базовый класс). Пул соединений увеличен до 50, чтобы параллельные сценарии упирались в блокировки базы, а не в нехватку соединений. Каждый тест создаёт свои счета с уникальными номерами, поэтому очистка между тестами не нужна, а порядок тестов не важен.

## Допущения по неоднозначным местам ТЗ

- Часовой пояс сроков карт UTC, максимальный срок действия карты 10 лет от выпуска.
- Повторная блокировка заблокированной карты и повторное закрытие закрытого счёта это ошибки, а не тихий успех.
- Неподдерживаемая валюта везде даёт код `INVALID_MONEY`, откуда бы ни пришла: для клиента это одна и та же ошибка.
- Сумма перевода задаётся в валюте счёта-отправителя, сумма зачисления вычисляется по курсу. Если она округляется до нуля, перевод отклоняется.
- Роли Operator и Admin это сотрудники банка и работают с любыми клиентами, поэтому проверки владельца счёта нет.
- Операции, запрещённые для заблокированной или просроченной карты: перевод с указанием этой карты, изменение карты, разблокировка просроченной.
- Журнал операций содержит только завершённые переводы, неудачный перевод откатывается и в журнал не попадает.
- Поддерживаемые валюты: USD, EUR, KGS, JPY, KWD, GBP.

## Тесты

- **Модульные тесты домена.** Ожидаемые значения заданы литералами, коды ошибок проверяются явно, после отклонённой операции проверяется, что состояние не изменилось. Покрыто: точность денег по валютам и формат суммы, округление курсов, инварианты счёта, переходы статусов карты и границы срока, алгоритм Луна и маскирование.
- **Интеграционные тесты** на реальной PostgreSQL: перевод, повтор с тем же ключом, тот же ключ с другой суммой, отказ не сжигает ключ, закрытие счёта с активной картой.
- **Конкурентные тесты**, три сценария: 20 параллельных переводов при нехватке средств (баланс не уходит в минус, сумма на счетах сохраняется), встречные переводы A→B и B→A (нет дедлоков), один ключ идемпотентности в 10 потоках (создаётся ровно одна операция).

## Что доделал бы при большем времени

В порядке приоритета:

1. REST-слой: контроллеры, DTO с валидацией, глобальный обработчик в формате Problem Details (RFC 7807) с кодами из доменных исключений, без стек-трейсов в ответах.
2. JWT и две роли (Operator, Admin), секреты только из окружения.
3. Клиенты и телефоны с фильтрами, сортировкой и пагинацией (offset для списка клиентов, keyset по `(created_at, id)` для выписки: журнал растёт без ограничений, а offset на больших смещениях деградирует).
4. Correlation id в логах и в ответе, JSON-логи, liveness и readiness, OpenAPI.
5. GitHub Actions и файл `.http` с примерами запросов.
6. Фоновый перевод просроченных карт в `EXPIRED`, outbox и доменное событие о переводе, журнал аудита, ledger-проводки вместо одной записи на перевод.
7. Rate limiting, кэширование курсов, повторы и circuit breaker для настоящего поставщика курсов.
8. Токенизация номеров карт или HSM вместо ключа из окружения, ротация ключей.
9. Мелкие unit-тесты: `null` в валютах `ExchangeRate`, `XAU` как исходная валюта, нулевая и отрицательная сумма при конвертации.

## Честно об ограничениях

Главное ограничение уже названо вверху: HTTP-слоя нет, поэтому сервис нельзя вызвать запросом, только через тесты. Вместе с ним отсутствует всё, что ТЗ относит к "обязательному минимуму" на уровне API: JWT и роли, валидация входных данных, OpenAPI, фильтрация и пагинация списка клиентов. Я это понимаю, и отмечаю, а не прячу.

Почему так вышло: за отведённое время я решил довести до конца то, что ТЗ называет определяющим качество, то есть корректность денег, атомарность и устойчивость к гонкам, идемпотентность, инварианты на уровне БД и защиту номеров карт. Эти части проверены тестами на реальной базе, включая сценарии, которые ломаются, если убрать блокировку или порядок захвата счетов. Остальное ложится поверх готового ядра прямолинейно: сервисы уже принимают команды и возвращают результаты, остаётся обернуть их контроллерами.

Из менее важного: заглушка курсов использует фиксированные значения для нескольких пар, а шифрование номеров ключом из переменных окружения подходит для демонстрации, но не для продакшена.
